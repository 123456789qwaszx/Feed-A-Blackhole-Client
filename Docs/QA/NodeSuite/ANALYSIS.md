# 첨부 노드 데이터 분석과 테스트 선정 근거

분석일: 2026-10-11. 입력: NodeCost.csv, NodeEffects.csv, Nodes.csv, UpgradeStats.csv, NodeCatalog.asset 및 사용자가 빨간 선으로 1~8번을 구분한 노드 배치 이미지.
게임 기준: QA 분리 변경 a683fc1 / 원격 개인 포크 feat/qa-setup 5926714. 첨부 노드 데이터는 이 기준의 게임 데이터와 의미상 동일하다. CSV 바이트 차이는 CRLF/LF이며 모든 열의 값이 같다. 노드 배치 에셋은 동일하다. 비용·효과 원본을 수정할 이유가 없으므로 변경하지 않았다.

## 1. 무엇이 확정이고 무엇이 해석인가

| 구분 | 근거 | 이번 작업에서의 사용 |
| --- | --- | --- |
| 확정 | Nodes의 NodeId·Rank 수 | 소유 상태의 유효 범위 |
| 확정 | NodeCost의 (NodeId, Rank, Cost) | 구매 비용과 예산 경계 |
| 확정 | NodeEffects의 (NodeId, Rank, StatId, Value, 단위) | 해당 Rank가 실제로 더하는 값 |
| 확정 | UpgradeStats의 기본값·Min·Max | 수치 계산 및 상한 |
| 확정 | NodeCatalog의 좌표·Start·Links | 배치·노출·구매 가능 경로 |
| 해석 | 이미지의 빨간 구획을 좌표에 대조 | 1~8번 구역별 기능 묶음. zones.json의 명시 목록으로 고정 |
| 테스트 가정 | 구역별 성장 단계 0~3 | 관찰할 전장 크기 선정. 자연 플레이의 도달 단계로 주장하지 않음 |
| 테스트 가정 | 이정표 목표 잔액을 구매 예산으로 사용 | 같은 노드로 이정표 전후 비교. 자연 플레이 평균 보유량으로 주장하지 않음 |

이미지에는 기계가 읽을 구역 ID나 경계 좌표가 없다. 경계 부근 소속은 검토 가능한 해석이다. 좌표로 최초 분류한 뒤 247개 전체를 zones.json에 명시했다. 이후 재배치되어도 테스트 소속이 자동으로 바뀌지 않는다. 이 목록과 zone-map.svg를 보고 경계 노드를 조정할 수 있다.

## 2. 데이터 관계와 무결성

- 노드 247개, 전체 Rank 319개, 수치 정의 60개, 무방향 연결 364개.
- 239개 노드는 Rank1, 중앙 2번 구역의 8개 노드는 각각 Rank10이다.
- 비용 319행, 효과 319행: 현재 모든 Rank에 비용 하나와 효과 하나가 있다.
- 노드와 배치 ID가 모두 일치하며 누락·미배치가 없다. 모든 배치 노드는 시작 노드에서 연결로 도달한다.
- 실제 Core의 NodeContentCsv.Load → NodeContentLoader → NodeTreeLoader로 검증했다. 시트의 ‘검사 OK’ 문자열만 보고 통과시키지 않았다.
- 전체 구매 비용은 47,326,272,937,772,307 Gold. 후반 비용은 32비트 정수 범위를 넘으므로 정수 long으로 다룬다.
- 모든 60 StatId는 Core에서 해당 UpgradeStat을 참조한다. 참조 파일·행·코드는 analysis.json에 담았다. 정적 참조 존재가 실제 전투·표현의 완성도를 증명하지는 않는다.

## 3. 구매 규칙에서 중요한 사실

NodeTreeLoader.LoadGraph는 Links를 양방향으로 만든다. 한쪽 노드에만 선을 적어도 같은 선이다. NodeGraph.IsRevealed는 시작 노드 또는 소유한 이웃 하나가 있으면 노출한다. 여러 이웃을 모두 사야 하는 AND 선행 조건이 아니다. Rank1을 사는 순간 이웃이 드러나며, Rank10까지 사야 다음으로 넘어가는 규칙도 아니다.

시작 노드는 timer-01, growth.time-01, electricAsteroid.spawnChance-01, supernovaStar.hpDamage-06 네 개다. 따라서 비싼 후반 시작 노드도 처음부터 노출될 수 있다. 구매를 막는 것은 가격이다. 구역 번호를 해금 순서로 사용하면 실제 규칙과 어긋난다.

전역 최저가 구매는 매번 ‘지금 드러났고 구매 가능한 다음 Rank’ 중 가장 싼 것을 고른다. 동일 가격은 NodeId ordinal 순서다. 구역별로 구매를 제한하지 않는다. 필요한 기능을 확인하는 최소 경로와 최저가 진행의 보유 상태는 서로 다르다.

## 4. 수치를 읽는 기준

UpgradeStatValues는 기본값 + Rank 효과 합을 Min/Max로 자른 뒤, GainOf = 현재 값 − 시트 기본값을 전투 정의에 전달한다. 전투의 기본값은 SO 에셋에 있다. 그러므로 시트 기본값만으로 최종 피해·효과 수치를 단정하면 안 된다.

- asteroid.count-01: +30마리. 기본 시작 공급 20에서 해당 노드만 추가하면 50마리.
- asteroid.toPlanet-01: Flat +52. EnemyComposition.UpgradeCount 및 GameSessionFactory의 Math.Min(have, UpgradeCount)에 따라 시작 공급에서 최대 52마리를 행성으로 옮긴다. 52%가 아니다. 시작 공급 20이면 20까지만 옮긴다. 변환은 판 조립 시 수행된다.
- planet.toStar 역시 시작 공급에서 다음 종류로 옮기는 수다. 별 성질 실험에는 행성과 별 변환 경로를 함께 준비했다.
- electricAsteroid.spawnChance-01: +10%p. 일반 적의 특수 성질 판정은 최대 하나다. 확률이 더해졌다고 매번 해당 성질이 나온다고 판정하지 않는다.
- electricStar.critBonus-02: 치명타 피해 +100%p. 전기 별 출현과 전기 별 치명타 확률을 off/on 공통으로 갖춰, 비활성 기능의 배율만 바꾸는 실험이 되지 않게 했다.
- comet.rainChance-02: 혜성 비 확률 +10%p. 혜성 출현이 먼저 필요하다. comet.spawnChance-01을 공통 기반으로 준비했다.
- 슈퍼노바: EnemyUpgradeStats.TraitHealthFraction → ExplosionDefinition → DeathEffects 경로에서 대상 현재 HP 비례 피해다. 최대 HP 비례로 기대하지 않는다.
- 확률 수치 일부는 100에서 잘린다. 이미 상한이면 추가 Rank가 실제 효과를 늘리지 않을 수 있다. full은 중첩·상한 테스트이며 효과가 모두 선형 증가한다는 가정이 아니다.

## 6. 세팅 설계

39개를 목적별로 나눴다. 사용자는 한 번에 전부 실행할 필요가 없다.

| 종류 | 수 | 고정하는 것 | 알아내려는 것 |
| --- | ---: | --- | --- |
| 노드 없는 기준 | 1 | 원본 콘텐츠·단계0·시드 | 기본 시간·공급·종료 |
| 구역 off/on | 16 | 같은 지원 노드·단계·시드·시간 고정 | 해당 Rank1 하나가 만드는 차이 |
| 구역 full | 8 | 구역 최대 Rank + 연결용 Rank1 | 중첩·화면·사운드·기능 부하 |
| 예산 레시피 | 8 | 전역 최저가 순서와 예산·시드 | 해당 기능이 최저가 진행에 최초 포함되는 구매 경계 |
| 이정표 전후 | 6 | 같은 보유 노드·Gold·시드 | Level10/20/30 경계, 결산, 다음 판 전장 |

지원 노드는 현재 소유 노드 또는 시작 노드에서 대상까지의 ‘추가 Rank1 비용 최소 경로’로 선택했다. 여러 대상은 순서대로 연결하므로 전체 연결 트리의 전역 최소 비용을 보장하는 알고리즘은 아니다. off/on은 대상 노드를 마지막에 추가하고 off에서 그것만 뺀다. 8쌍 모두 차이가 노드 하나뿐인지와 소유 경로의 구매 가능성을 실제 Core로 검증했다.

full은 해당 구역 최대 Rank를 가진다. 대상 적 출현에 필요한 지원 기능 및 타 구역 연결용 노드는 Rank1만 포함한다. 구역별 full끼리는 보유 상태가 다르므로, 성능 결과를 구역 효과만의 인과 비교로 해석하면 안 된다.

모든 시드 기본값은 20261011. 시간 고정은 관찰용 off/on/full에만 사용했다. 예산과 이정표는 정상 시간으로 실행한다. 시드는 초기 난수를 고정하지만 사용자 입력까지 재현하지는 않는다. 기능 on/off가 난수 소비량을 바꾸면 이후 위치·판정도 달라질 수 있다.

contentFingerprint는 임의 해시를 넣지 않고 비웠다. analysis.json에 원본 파일 SHA-256을 기록했고 Unity 검사 메뉴가 실제 콘텐츠 지문을 출력한다. Python 파일 해시를 게임의 콘텐츠 지문으로 위장하지 않았다. Unity에서 세팅을 ‘다른 이름으로 저장’하면 실제 지문을 가진 스냅샷을 만들 수 있다.

## 8. 이정표 선정 근거

첨부 파일에는 성장 사다리·보상이 없어 게임의 HqGrowthSetup.asset과 HqGrowthDefinition/HqMilestone을 추가로 읽었다. Level10/20/30, 목표 잔액 690,000 / 5,600,000 / 420,000,000, 전장 배율 1.68 / 2.27 / 2.83이 기준이다.

결산 보상은 고정 추가 Gold가 아니라 목표 잔액까지의 차액이다. 이미 소지금이 더 많으면 깎지 않는다. qa-mark의 Gold는 0으로 두고, 목표 잔액을 별도의 노드 예산으로 해석해 만든 보유 목록을 before/after에 동일하게 넣었다. 이 예산 가정은 결산 보상 검증과 혼동하지 않는다.

before는 단계0/1/2의 Level9/19/29, after는 단계1/2/3의 Level10/20/30이다. 단계3은 다음 이정표가 없어 시간 종료를 확인한다. 시작 Level을 올리는 것은 실제 EXP·성장 공급 경로를 사용하므로 자연 플레이 도중 적 위치·HP·난수 상태 복원이 아니다. 이정표 전후가 전장 외 모든 런타임 상태를 통제한 비교라고 주장하지 않는다.

## 9. 검증 결과와 남은 확인

완료: Core 전체 컴파일, 실제 CSV·노드 그래프 로드, 39개 파싱·ScenarioRunner 적용, 전체 소유 경로 연결, 8개 예산 결과, 8쌍 단일 노드 차이, 3쌍 동일 노드 경계, 고정 시드·최종 Gold 확인.
