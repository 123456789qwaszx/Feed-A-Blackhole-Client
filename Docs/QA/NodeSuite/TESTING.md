# 팀원이 실제로 테스트하는 순서

## 준비

1. QA 세팅 체계가 있는 feat/qa-setup 기반 브랜치를 받는다. 이 묶음은 AI·Sheets를 호출하지 않는다.
2. Unity에서 GameScene을 열고 컴파일 오류가 없는지 확인한다.
3. BlackHole > QA > Validate Node Suite를 실행한다. 현재 에셋으로 39개 세팅을 판 조립하고, PlaytestLibrary를 다시 모은다. 생성 결과는 PlaytestData/node-suite-validation.md다.
4. 이 검사는 플레이 모드를 켜지 않는다. 판 조립 오류나 연결 누락이 있으면 먼저 해결한다. 실제 실행하지 않은 검사 결과를 통과로 기록하지 않는다.
5. BlackHole > Test Setup에서 원본 프로필을 선택하고 QA 분류를 고른다. 세팅을 불러온 뒤 ▶ 이 세팅으로 플레이한다. F1은 개발 패널이다.
6. 세팅을 불러온 뒤 임의로 노드·단계·시드를 바꿨으면 ‘다른 이름으로 저장’하고 그 파일 이름으로 기록한다.

## 첫 테스트 회차: 9개

| 순서 | 파일 이름 | 볼 것 | 통과 기준 |
| --- | --- | --- | --- |
| 1 | qa-node-first | 기본 판 | 노드 없음, 기본 12초, 시작 공급20, 종료·결산·재시작 |
| 2 | qa-zone01-on | 기본 수량 증가 | off와 비교해 +30, 시작 공급50. 적 위치·카메라·공격 구분 |
| 3 | qa-zone03-on | 전기 소행성 | 확정 정보에 성질 확률 증가. 실제 사망 효과·피해·음향 |
| 4 | qa-zone04-on | 행성 변환 | 확정 정보의 변환 수와 초기 적 수가 일치. 52%로 판정하지 않음 |
| 5 | qa-zone06-on | 전기 별 | 별 공급과 전기 성질 확률이 있고 실제 번개 효과 확인 |
| 6 | qa-zone07-on | 레이저 별 | 별 공급과 레이저 성질 확률. 예고와 발사·피해 구분 |
| 7 | qa-zone08-on | 슈퍼노바 | 현재 HP 비례 피해·범위·사망 효과·음향 확인 |
| 8 | qa-mark10-before | Level9→10 | 이정표 도달 시 판 종료, 성장 단계 상승, 결산 목표 잔액 확인 |
| 9 | qa-mark10-after | 다음 판 Level10 | 단계1 시작과 전장 배율1.68. 노드가 before와 동일 |

특수 성질은 확률이다. 한 판에 안 나왔다고 실패로 판단하지 않는다. 먼저 창 ‘확정 정보’에서 대상 종류 공급·성질 확률을 본다. 시각·음향만 빠르게 검수하려면 F1 적 탭에서 종류·성질을 지정해 소환할 수 있다. 이 경우 기록에 ‘강제 소환’을 남기고 확률 검증으로 세지 않는다.

기능 판에서 치명타나 피해가 잘 안 보이면 대상을 먼저 고립시키고 HUD·처치 기록을 확인한다. 전기 별 치명타 배율 비교는 지원 노드에 치명타 확률을 포함했지만 확정 치명타는 아니다. 동일 시드만으로 입력이나 모든 후속 난수까지 같아지는 것은 아니다.

## 두 번째 회차: 원인 분리

해당 구역의 qa-zoneNN-off를 실행하고 qa-zoneNN-on을 실행한다. 두 파일은 대상 Rank1 하나만 다르다. 비교는 같은 원본 콘텐츠·프로필·시드·조준 방법으로 실시한다. 창 ‘확정 정보’의 바뀐 수치부터 확인한 다음 실제 표현을 확인한다.

관찰용 off/on과 full은 시간 고정이다. 남은 시간이 줄지 않는 것은 정상이며 제한 시간 밸런스의 검증에 사용하지 않는다. 시간 고정은 Level 이정표 종료를 막지 않는다. 빠르게 이정표에 닿아 관찰이 끊기면 세팅을 단계3·시작Level0으로 복사해 저장하고, 변경된 세팅 이름을 기록한다.

2번 구역은 마지막에 확인한다. 8개 Rank10의 후반 증폭 구역이다. qa-zone02-off/on으로 전기 별 치명타 배율만 먼저 확인하고, full에서는 상한·반복 구매·수치 중첩을 확인한다. 5번 구역은 혜성 비와 행성 공급을 확인한다.

## 예산 진행

QA/예산에서 qa-budget-zoneNN을 선택한다. 이 파일은 노드 목록을 비워 두고 autoBuyBudget으로 모든 드러난 노드 가운데 가장 싼 다음 Rank부터 구매한다. 최종 소지금 gold는 0이며 구매 예산 잔액은 버린다.

창에서 불러오면 노드 목록으로 해소된다. ‘다른 이름으로 저장’하면 autoBuyBudget=0인 확정 스냅샷이 된다. 원래 레시피를 덮어쓰지 말고 qa-budget-zoneNN-observed 등의 이름으로 저장해 팀에 공유한다. 같은 예산이어도 가격·연결·Rank가 바뀌면 결과는 달라진다.

검증 당시 정확한 목록은 analysis.json의 presets[].resolvedNodes에 있다. 최초 포함 예산은 ANALYSIS.md에 있다. 이 금액은 자연 도달 시간·권장 가격을 의미하지 않는다.

## Level20/30와 결산

qa-mark20-before/after 및 qa-mark30-before/after를 같은 방식으로 비교한다.

| 경계 | before | after | 목표 잔액 | 다음 판 전장 배율 |
| --- | --- | --- | ---: | ---: |
| Level10 | 단계0 / Level9 | 단계1 / Level10 | 690,000 | 1.68 |
| Level20 | 단계1 / Level19 | 단계2 / Level20 | 5,600,000 | 2.27 |
| Level30 | 단계2 / Level29 | 단계3 / Level30 | 420,000,000 | 2.83 |

성장도는 이정표를 달성한 횟수이며 Level과 같은 값이 아니다. 목표 잔액은 판에서 번 Gold에 추가로 더하는 고정 보상이 아니다. stage3에는 다음 이정표가 없으므로 시간 종료를 확인한다.

before/after는 적 전체 상태를 저장·복원한 것이 아니다. 시작 Level을 채우는 과정에서 성장 공급이 추가될 수 있다. 카메라 경계 검증과 자연적인 적 밀도·도달 시간 검증을 구분한다.

## 구역 full: 중첩·표현·부하

qa-zoneNN-full은 해당 구역 모든 Rank와 필요한 연결·출현 노드를 갖는다. 단계3으로 이정표 종료를 피하고 시간을 고정했다. 동일 조준 위치와 관찰 시간을 정해 화면 구분·소리 겹침·프레임·최대 적 수를 확인한다. 다른 구역 full과 노드가 다르므로 단순 수치 차이를 해당 구역만의 영향으로 결론 내리지 않는다.

과도한 수치는 기능 상한을 확인하는 조건이다. 이 조건에서 ‘재미있다/너무 쉽다’를 출시 밸런스로 판단하지 않는다. 실제 처음부터 하는 플레이는 정상 시간·자연 구매로 별도 실시한다.

## 기록 형식

PlaytestData 메모는 PC별로 남는다. 공유가 필요하면 아래 형식으로 이슈나 팀 문서에 옮긴다. 빌드와 세팅 이름이 없는 느낌만으로 수정하지 않는다.

```text
검수자 / 날짜:
커밋 또는 빌드:
세팅 이름 / 프로필 / 콘텐츠 지문:
시드 / 조준 방법 / 관찰 시간:
강제 소환·배속 등 추가 조작:
확인할 결과:
실제 결과:
판정: 통과 / 실패 / 미확인
재현 순서:
스크린샷 또는 영상:
```

## 다시 생성·자동 검사

레포 루트에서 아래를 실행한다. Python 생성기는 표준 라이브러리만 쓴다. 런타임에 Python이 필요한 것은 아니다.

```sh
python Tools/QA/build_node_suite.py
dotnet run --project Tests/QA/QA.csproj
```

생성기는 zones.json의 검토된 소속을 사용한다. CSV·배치·성장 에셋을 읽어 세팅, 비용 근거, 검증 fixture를 갱신한다. 생성 후 diff에서 바뀐 노드·비용·단계를 검토한다. zone-map.svg와 설명 문서의 수치는 자동 갱신하지 않으므로 데이터가 바뀌면 함께 점검한다. 구역 소속을 바꿀 때는 zones.json을 먼저 고친다.

.NET 검사는 JsonUtility 테스트 shim을 사용한다. Unity 직렬화와 실제 에셋 조립은 Unity 메뉴로 확인하고, 플레이 표현은 사람이 검수한다.
